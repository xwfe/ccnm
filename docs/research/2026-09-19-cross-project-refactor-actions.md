## 2. 最先补的是执行契约，不是更多工具

### C-A：与 gld 对齐后台任务、会话和租约；主评审 X04

P41 后台命令受 server 会话绑定，连接结束会停掉。gld 的 coding 会话目前按 120 秒无调用回收；其空闲判据不追踪启动调用已返回后的远端进程。两层组合可能杀掉仍在运行的后台任务，本轮尚未执行长时复现。

ccnm 应提供权威生命周期说明，gld 负责连接租约与状态投影。近期保留现有 session-bound 契约，明示续租/到期/停止原因。未来 durable Job、跨连接恢复是独立协商能力或协议版本变更，不能在 `/1` 下悄悄改变断开即停。

分别定义：等待一个工具结果、运行一个命令、持有 coding 会话、保留输出。取消等待是否取消命令也要说清楚。gld 单次调用预算和等待上限不是 Runtime 的运行时限。

验收：后台运行超过 hub 空闲阈值、连接正常结束、网络中断、重复停止、旧 output_ref、租约到期各有真实二进制组合测试；传输失败不自动重放可能已经执行的写命令。不能凭 gld 的 HTTP 状态给远端进程伪造终态。

**落地情况（2026-09-20）**：ccnm 这半边是 P42（`438e6be`、`ab1eef7`，记录 [p42](p42-lifecycle-contract-2026-09-20.md)）——协议第 6 节写清四个时钟和三句契约（session-bound 是权威语义、取消等待不等于取消命令、终态只有 Runtime 说了算），三条没护栏的语义补成回归测试，**没有改任何行为**。gld 那半边同日做完（gld `85bda77`、`9e6ecc1`）：真实组合跑出三条并都修了——前台命令期限超过它的调用预算、空闲回收看不见在跑的后台命令、连接关得太急导致 ccnm 被强杀后在 Runtime 上留孤儿。**还没做的**：租约显示与续租预算、durable Job（要升 `ccnm.workspace-mcp/2` 或显式协商）、真实 Host 或真实模型经 hub 用后台命令。

### C-B：故障清理与写权恢复；主评审 X03/X05

现有 `mcp/write_guard.rs` 通过 OS 文件锁与持久 `held` 标记拒绝异常后的自动交权，保留这项设计。P41 已注明 SIGKILL server 时可能残留子进程；这是清理/可用性缺口，不应被误报成“没有写锁防护”。

补进程归属证据与恢复诊断，分别验证 server 强杀、后代脱离进程组、管道残留、监督者死亡和主机重启。只有能证明旧写者结束才能转移写权；做不到自动恢复时保留 unknown/拒绝转移，不能按时间清锁或只检查一个 PID。

明确 state authority：锁存于传入 state 目录，同一物理树不能以另一个 state home 创建第二个互不知晓的写域。与 gld 本地重复登记时近期选一个执行权威，而不是立即造一套跨产品共享锁服务。

当前 Git common directory 资源键把相关 worktree 一并串行，是保守边界。将来 Orchestrator 要并行 worktree 时，需要工作树文件与公共 Git 元数据的协调设计，不因“多 Agent”需求直接放开现有锁。

验收：不允许未知旧写者与新写者同时获得受管权限；清理不成功时能定位准确资源和恢复步骤。会话内后台 exec 与 patch 的竞争另测，单写会话不能替代所有内部写入协调。

**落地情况（2026-09-20）**：P43（`e523432`、`10450d8`，记录 [p43](p43-guard-recovery-2026-09-20.md)）。故障注入跑出一条真缺口并修了：一个离开进程组又攥着管道的后代留下时，server 照常正常退出并把写锁标成 released，下一个 coding 会话就在同一棵树上开起来——正是「不允许未知旧写者与新写者同时获得受管权限」禁止的。现在 `stop_all` 返回它放弃了哪几条，server 退出前非空就不放锁，marker 留成 `held` 加一行 `abandoned` 并点名还剩哪个 `output_ref`；`ccnm status` 和拒绝信息都分得清「故意留着的」和「异常退出留下的」。marker 里记 pid，**pid 不在从来不是交权的理由**。同时写清了一条一直存在却没有文档的边界：同一棵树配两个 `XDG_STATE_HOME` 就是两个互不知晓的写域（实测两个 coding 会话都写进去了）。**没做的**：进程容器（cgroup / job object / supervisor）——没有它，脱离进程组但**不占管道**的后代 ccnm 发现不了，锁照常交出去，这条边界写在支持矩阵里；主机重启后的自动恢复也没做。

### C-C：服务端能力与输入校验；主评审 X06/X10

gld 已拦截远端没有的工具名和顶层字段，但外部 CLI 可以直接连 ccnm，所以服务端仍须自行验证。优先明确影响副作用的字段、嵌套 `apply_patch` 操作、类型/枚举、后台模式和输出引用寿命，避免不支持的请求被静默忽略。

已冻结契约允许加法，不代表所有行为修改都算加法。引入未知字段拒绝或新的生命周期前，核对 `/1` 原有容错承诺；必要时用新版本或显式协商，不一边要求旧客户端不变、一边全局切换解析行为。

补运行构建/能力代次和实际工具表的诊断，与 gld 对齐但不要求两产品所有结果形状相同。连接换代不复用旧句柄，失败不回退另一执行后端。

验收：新旧客户端/Runtime 组合、不认识的安全相关字段、嵌套操作、错误类型均在执行前给明确结果；不支持与传输失联区分；声明的 schema 与真实解析一致。

**落地情况（2026-09-20）**：P44（`e2dfa0a`、`a3ee849`，记录 [p44](p44-input-validation-2026-09-20.md)）。未知字段以前在顶层和嵌套里都被静默丢掉，而 `inputSchema` 里一个 `additionalProperties` 都没有——声明和实现一起在说「随便加字段」。现在按用户定的力度分两档：`exec_command`、`apply_patch`、`stop_command` 连同 `files[]` 的嵌套结构拒绝未声明字段（落盘之前拒，并列出合法字段名），超界的 `timeout_ms` / `preview_bytes` 也从静默钳制改为拒绝；只读七个照常回答，但结果里写明忽略了什么。schemars 跟着 serde 自动发 `additionalProperties`，所以声明与解析一次对上，fixture 和 `published_tool_tables_match_the_running_server` 都跟着比它。**这是收紧不是加法**，不升 `/2` 的理由写在协议页首。能力代次（X10）不用另造：`serverInfo.version` 加 `tools/list` 就是。**最要紧的没验项**：真实 Host 会不会给工具塞多余字段——没额度没登录，是推理不是证据。**没做的**：MCP 层的能力协商扩展（SEP 那条另立）。

## 3. Agent 面恢复的建议边界；主评审 X08/X09

沿 toexec v3 的既定决策实施：**WebSearch 默认开放，WebFetch opt-in**。不重复要求用户决定这两项。其余子代理、todo、提问、计划模式分组验证，再决定启用集合；不恢复本机文件/命令执行能力。

开工先核对当前实际受测官方 CLI 版本的启动参数、可用工具、子代理继承与动态工具发现。允许集控制第一层，原有 deny 作第二层。项目 skill、hook、项目级 MCP 和脚本不能在持有 AI 凭据的 Agent 机器上执行。

skills 工具通道已存在，先验证真实 Host 是否收到完整目录、能否加载附件和恰当使用；不自动执行命令注入。解析结果、宿主激活与执行授权分开，忽略字段应告知原因，不把 `allowed-tools` 当作 Runtime 的安全上限。

MCP 官方 Skills 扩展不能视为简单加两个方法：当前稳定规范基于 MCP `2026-07-28` 或更新协议，并有发现协商与资源清单要求；本会话 gld 仍报告 `2025-06-18`。先核对协议/Host 支持，另立范围，保留现有工具通道。依据与外部规范链接见主评审 R4/R5。

验收：未知新增内置工具默认不启用；子代理不恢复 Agent 本地执行旁路；未 opt-in 的 WebFetch 不可用；真实模型是否主动使用能力单独记证据。源码/假模型测试不能替代真实模型回合，当前评审不沿用历史额度授权。

## 4. 共享库与平台的边界；主评审 X01/X11

toexec 当前 Windows 文件替换存在先删后 rename 的风险，需要共享库和 gld 优先修。ccnm 配合复核依赖采用后的 Unix 事务、权限和恢复行为，不借这次库更新扩展成 Windows Runtime 实现。

继续分别记录 Agent/Controller 与 Runtime 的平台覆盖；Linux Runtime 已验不代表 Linux Agent 可用，native exec-server 的旧 Debian 真机证据不代表当前 MCP 新能力已在 Linux 验收。

后续优先一个 macOS Agent/hub → Linux Runtime 的当前构建闭环，再为 Windows 明确第一角色并立 RFC。文件路径、权限、进程树、stdin/PTY、服务管理和 bridge 依赖必须一起考虑，不预先承诺三客户端三平台已经支持。

共享库只承接机制，路径授权、进程权限、writer guard、journal 与恢复责任仍在 ccnm。零依赖不是正确性的替代物，也不因此先建新的大内核。
