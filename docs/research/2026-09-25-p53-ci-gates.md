# P53：计划、协议与 Python 测试接入 CI 和发版（C51-03）

日期：2026-09-25。起点 `main` / `daea088`。缺口的来源见 [P51 审计的 C51-03](2026-09-23-lifecycle-and-docs-audit.md)：CI 和发版只跑 Rust，Python 中立客户端测试、`check_plan.py`、`check_protocol.py` 都不在里面，CI 绿说明不了契约和真实二进制的行为。

## 结论

- 新增 [`scripts/ci_gates.py`](../../scripts/ci_gates.py)，本地和 CI 同一条命令：自己 `cargo build -p ccnm-cli`，把刚构建出的二进制交给 `CCNM_BIN`，依次跑计划检查、协议检查和 `tests/` 下全部 Python 测试；**任何 skip、失败、出错、一条都没跑，或者 `CCNM_BIN` 不是 ccnm，都让它退出非零**。
- `ci.yml` 的 macOS 与 Linux job 在 Rust 测试之后跑它；`release.yml` 两个平台 job 把它放进「门禁」那一步，排在构建和上传之前，`publish` 仍要两个 job 都绿。
- 本机：门禁通过；各种"看着像通过"的情况都能让它变红（下文）。**GitHub runner 上的结果见最后一节。**

## 漏洞本来有多大

在不含 `target/` 的仓库副本里用 P53 之前文档写的命令跑：

```text
python3 -B -m unittest discover -s tests -q
Ran 210 tests ...
OK (skipped=95)        # 退出码 0
```

210 条里 95 条——所有驱动真实二进制的测试类——因为找不到二进制整类跳过，结果照样是 `OK`。CI 缓存恢复出的旧 `target/` 则是另一面：测试跑的是旧二进制。`ci_gates.py` 每次都构建，路径取自 cargo 报告的产物，并把 skip 判成失败。

## 平台前提（P53.1）

| 要的东西 | 谁用 | CI 里怎么来 |
| --- | --- | --- |
| 当前提交构建出的 `ccnm` | 9 个驱动真实二进制的测试类，全部经 `CCNM_BIN` 取路径 | `ci_gates.py` 自己 `cargo build -p ccnm-cli`；cargo 按指纹重编，缓存里的旧产物不会被直接拿来用 |
| `python3` 3.9 起 | 全部 Python 测试与两个检查脚本，只用标准库 | runner 自带（ubuntu-24.04 为 3.12；macos-latest 自带），不加 setup-python |
| `git`、`rg` | 中立客户端的 `list_files` / `search_text` | runner 自带 git；工作流原本就装 ripgrep |
| `/bin/ps`、`/bin/kill`、`/bin/cat` | relay 进程组收尾（P52） | 两种 runner 都有；Ubuntu 的 `ps` / `kill` 来自 procps |

可解释的 skip 只有两处，在 CI 机器上都不该触发，所以 `ALLOWED_SKIPS` 留空：`test_p3_runtime_user_script` 的两条在 root 下跳过（runner 账号不是 root）；`test_p12_dogfood` 的身份审计用例在"本身就是合格执行身份"的账号上跳过（runner 账号有 sudo/admin，审计会拒绝，用例照常跑）。runner 上若真触发，门禁会红并写出 skip 原因，那时再判断是写进 `ALLOWED_SKIPS` 还是修测试。

## 失败会挡住发布（P53.2、P53.3）

本机证据，不是 runner 结果：

- [`tests/test_ci_gates.py`](../../tests/test_ci_gates.py) 的策略测试对临时测试目录跑真实脚本：skip、失败、导入出错、一条都没跑、二进制不是 ccnm，退出码都非零；正常时为 0 且测试看得到 `CCNM_BIN`；`GITHUB_ACTIONS=true` 时失败清单同时作为注解输出。
- 同一文件的工作流测试用文本读两个 yml（CI 的系统 Python 不一定有 PyYAML）：CI 两个平台 job 各有一步跑 `ci_gates.py`；release 两个 job 里门禁那一步先于 `actions/upload-artifact`；`release.yml` 里没有 `continue-on-error` 和 `always()`；`publish` 是 `needs: [macos, linux]`。改工作流之前这两条是红的，改完变绿。
- 另用 PyYAML 在本机独立解析一遍，结论相同：release 的 `macos` / `linux` 都是「Gate（Rust 测试 + ci_gates）→ 构建 → 校验版本 → 上传」，没有条件步骤；`publish` 依赖两者。GitHub 不写 `shell` 时 `run` 用 `bash -e`，门禁里任何一条命令失败，这一步就停。
- 两个 CI 平台 job 都有 45 分钟超时（macOS 这次新加），两个 release 平台 job 新加 60 分钟：新门禁会起真实进程，挂住时不能占着 runner 六小时。Linux 那一步另套 `timeout 10m`，和 Rust 测试一样。
