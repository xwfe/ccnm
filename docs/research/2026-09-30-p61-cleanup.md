# P61 跨身份清理与结果失效（2026-09-30）

范围见[输出与清理方案](../plan/core-output-cleanup.md)第 2 节，现状来自 [P57 记录](2026-09-28-p57-core-baseline.md) 第 3.7 节（E）。本轮只做离线实现与回归：**没有连 hpsrv/fodelf、没有运行真实模型或真实 Controller、没有部署或推送。** 三个账号用同一用户下的三个 state 目录模拟，**不是跨 UID 的权限证明**，那一条留给 P62。

## 1. 结论

清理现在先预览、再由各自的账号删自己的东西：Agent 删它的会话记录，Runtime 执行账号删 `exec_command` 留下的输出，Operator 删自己的 Machine API 输出拷贝并把记录留成墓碑。之前 `workspace remove --purge` 让 Agent 把 workspace 的会话目录全删（跑着的也删），再删"敲命令这个账号"自己 state 下同名的目录——分离部署下那不是执行账号的目录，执行账号的输出和 RPC 记录没人管，workspace 配置却照删，之后再没有命令能找到它们（P57 E）。

## 2. 改了什么

### 2.1 谁的东西谁删

新模块 [cleanup.rs](../../crates/ccnm-core/src/cleanup.rs)：

| 账号 | 删什么 | 在哪（它自己的 state） | 谁来删 |
| --- | --- | --- | --- |
| Agent | 已结束会话的 `sessions/<id>/`；`--purge` 时加 `workspaces/<name>/` | Agent Node | `ccnm internal agent-cleanup` |
| Runtime 执行账号 | 已结束会话的 `sessions/<id>/output/` | Runtime Node，执行账号 | `ccnm internal runtime-cleanup`，由 Agent 经它到 Runtime 的那条 ssh 调 |
| Operator | `rpc/outputs/<handle>/`，以及记录里的最终回答和尾巴 | Runtime Node，Operator 账号 | `ccnm cleanup` 本进程 |

为什么 Runtime 那一半要经 Agent：Runtime 的输出目录不记属于哪个 workspace、会话怎样结束，只有 Agent 的会话记录知道；而能落到执行账号上的只有 Agent 那条 ssh（和 P60 的写锁观察同一条路）。

会保留、并给出原因的（`Why`）：`not_ended`、`unknown`、`guard`（Runtime 写锁不空闲且标着这个会话，或标着的是认不出的名字——恢复要用它的记录）、`in_use`（有 `mcp-serve` 服务它、命令还在跑、会话控制锁被占、输出拷贝正在写）、`not_a_directory`（符号链接等）、`foreign_owner`、`unchecked`（`ps` 跑不了）、`runtime_not_asked`、`runtime_half_pending`、`changed`。

只看这个 workspace 的东西：Agent 只列目录名是会话 id、记录里的 workspace 正是它的会话；Runtime 只看 Agent 点名的会话 id，而且在拼任何路径之前先校验每个 id 必须是会话 id；Operator 只看记录里 workspace 相符的。不扫整台机器，不按用户名或通配符。

### 2.2 预览、令牌与 apply

- `ccnm cleanup <ws>`：向三方收清单，逐项列出角色、uid、类型、会话/句柄、大小、打算删还是留及原因，最后给出 `ccnm cleanup <ws> --apply <令牌>`。
- 令牌是 `<过期时间>-<哈希>`，哈希覆盖：过期时间、workspace 的 root、Agent 引用与节点、Runtime 节点、答话的 Agent 身份、三方 uid、每一方是否问到、以及每一项的角色/类型/id/大小/版本/计划。版本是该项目录下的总字节数和最新修改时间，写了、换了、删了任何文件都会变。令牌不是秘密，只用来确认"删的就是看过的那份"。
- `--apply`：令牌格式不对 → `CCNM_E_INVALID_ARGS`；过期 → `CCNM_E_NOT_READY`；重新向三方收一遍清单算出的令牌不同 → `CCNM_E_NOT_READY`（`no longer what was previewed`），一个都不删。对上了再按项执行，每个节点删之前把这一项再和现状核对一次（计划、版本），不符就跳过。
- 执行顺序：Operator 自己的；然后一次请求交给 Agent，Agent **先**请 Runtime 删，Runtime 那一半没删掉（失败、跳过或连不上）的会话，Agent 的记录跳过（`runtime_half_pending`），因为以后找那份输出只能靠它。Agent 删会话目录前先非阻塞地拿 P58 的会话控制锁，拿不到就让开。
- 退出码：预览 0；apply 时计划删的都删了、三方都问到了为 0，否则 3。预览时本来就说要留的不算失败。

### 2.3 `workspace remove --purge` 与旧协议

`--purge` 用同一服务，`--purge` 本身就是确认，不再要令牌；多删 Agent 上这个 workspace 的 CLI 工作目录（仍有会话没结束时保留）。**只要有任何东西没清掉，workspace 就留在配置里、退出码 3**：配置是以后唯一还能找到那些东西的入口。不带 `--purge` 的 `workspace remove` 行为不变。

没有 Agent 节点的 workspace（只给外部 MCP 客户端用）不问 Agent：它在 Agent 上本来就没有会话，外部会话的输出断开时已由 Runtime 删掉。

新 Agent 收到旧 Operator 的 `agent-purge`（协议 1）一律 `CCNM_E_VERSION`，不再照旧删；旧 Agent 不认识 `agent-cleanup`，预览会说 Agent 问不到，什么都不动。Operator 不再删自己 state 下同名的 `sessions/<id>/`——那正是 P57 E 删错身份的地方。

### 2.4 结果失效与幂等

RPC 记录新增 `cleaned_at`。`Store::clean` 在 store 锁下先写墓碑（最终回答、stdout/stderr 尾巴清空，launch 输入、状态、outcome、`start_key` 原样），再删 `rpc/outputs/<handle>/`；拷贝正在写（目录里有 `.tmp`）就什么都不动。清过的会话：

- `session.result` → `-32012`，`reason: cleaned`，`data.session` 是句柄；旧游标同样；
- `session.status` 照常；
- 同一 `start_key` 的 `session.start` 仍返回原会话（`reused: true`），不派发；
- 墓碑已经没有拷贝时不再出现在清单里；万一有个在墓碑写下之前就开始的读取又把拷贝建了出来，下次预览会把它当作可删项列出。

## 5. 调用方看得到的变化

- 新命令 `ccnm cleanup <ws> [--apply <令牌>]`，只在定义 workspace 的那台（Runtime Node 的 Operator）上跑。名叫 `cleanup` 的 workspace 从此要写全 `ccnm run cleanup`（子命令优先的老规矩）。
- `workspace remove --purge`：输出从"删了 <路径>"改为按项的表；有东西留下时**不再删配置**、退出码 3；Operator 自己 state 下的同名 `sessions/<id>/` 不再删。
- Machine API：清过的会话 `session.result` 回 `-32012`（`reason: cleaned`），其余方法照旧。清理之前的一切行为不变，结果也不会自动过期。
- 两端要同一构建：清理用内部协议 10；旧 Operator 的 `agent-purge` 被新 Agent 以 `CCNM_E_VERSION` 拒绝。

## 6. 未覆盖与边界

- 没有真机、没有真实模型、没有 Linux、没有跨 UID：全部是 macOS arm64 上同一用户的三个目录。hpsrv/ccrun 复验在 P62。
- 不自动过期：没有 TTL sweep，Runtime 输出原有的 7 天过期不变；RPC 墓碑与 `start_key` 永远留着，何时可以遗忘旧键要另定政策。
- P61 之前用旧 `--purge` 删过的 workspace，执行账号那边可能剩下孤儿输出：没有 Agent 记录就找不到属于谁，只能等 7 天过期或由执行账号手动删。
- 竞态窗口：Runtime 在"核对没人服务"和"删除"之间，一个 `/mcp Reconnect` 恰好为同一会话起了新 `mcp-serve`，它新写的输出可能被删（与 7 天过期的扫描是同一个窗口）；Agent 侧 `agent-result` / `agent-output` 读取不拿会话控制锁，删除正好发生在它打开文件之前会读失败。
- 不是恢复工具：不杀进程、不动写锁；写锁标着的会话要先按运维手册处理。
- 跨节点删除不是事务：已删的不会回滚；每项报告 removed/skipped/failed，重新预览即可对剩下的重试。
