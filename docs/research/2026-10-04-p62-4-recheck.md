## 4. 6.1 监督进程丢失（F22）

驱动脚本在 hpsrv 上以 Operator 跑，只 import 仓库的 `ccnm_machine_client.py`：Machine API 起一个"用 `exec_command` 前台跑 `sleep 60 && echo P62C-LOST-<token>`"的 Claude 任务，另一个连接每 0.5 秒看一次 `session.status`。

**第一次没注入成**（模型 1/4）：放到 hpsrv 后台看状态的进程没有脱离 ssh，那条 ssh 一直挂到会话结束才返回，轮询命令的循环在任务跑完之后才开始，所以什么都没杀。会话正常完成（67 秒，$0.0900，回答 `P62C-LOST-182234`）。这是编排脚本的问题，改成在本机后台挂着看状态的 ssh 后重来。

**第二次**（模型 2/4）：

| epoch | 事 |
| --- | --- |
| …192.24 | `session.start` 返回，Agent 上的会话 `283aa222…` |
| …221.89 | hpsrv 上看到 ccrun 的 `sleep 60`（`bash -c sleep 60 && echo …` 的子进程） |
| …228.08 | fodelf 上核对 `supervisor.pid`（44731）的命令行是 `…/ccnm-p62c/ccnm internal supervise --payload …`、会话目录里还没有 `exit`，发 SIGKILL。Claude（44735）随即被 launchd 收养（ppid 1） |
| …229.29 | 调用方看到 `unknown` |

`session.result`：`state: unknown`，`failure` 是 `{"code": -32603, "ccnm_code": "CCNM_E_INTERNAL", "detail": "ccnm internal agent-run on fodelf failed (no exit status reported): the supervisor is gone and left no exit record at ~/.local/state/ccnm-p62/ccnm/sessions/283aa222…/exit; how the Agent ended is unknown, and the Agent it started (pid 44735) may still be running -- see ~/…/supervisor.log"}`；`output.unavailable_reason: agent_refused`（Agent 答的是"还没结束"）。对它再调 `session.stop` 回原样的 `unknown`，不改终态。

之后：Runtime 上的命令照常跑完（输出 `P62C-LOST-182920` 留在 ccrun 那边），被收养的 Claude 在命令结束后几秒内自己退出（它的 stdout 通往已经死掉的监督进程，Agent 上的 `stdout` 是 0 字节），`mcp-serve` 随之退出，写锁标记 `released`。Agent 上没有替它写 `exit`，`ccnm log` 记"没有结束记录"——没人看见它结束，这是有意的。

## 5. 6.2 分页的源头丢失（F23）

模型 3/4（$0.0240）：任务"把 `P62C-PAGE-<token>` 一行重复 40 遍，不用工具"。**只用 `session.status` 等到 `completed`，不调 `session.result`**，确认 Operator 上还没有这个会话的输出快照；在 fodelf 上确认会话目录里还没建过视图（没有 `stdout.view`），把 `stdout`（2510 字节）改名挪开，再调 `session.result`：

- `output`：`bytes_total 0`、`tail ""`、**`unavailable_reason: agent_refused`**；Operator 日志记 Agent 的原话 `the session's stdout is gone: it was created when the Agent started and is no longer at …/stdout, so there is no complete output to serve`。
- `text` 是完整的 40 行（会话结束时就从结果里解析好了）。
- 参考客户端 `read_output` 回 `complete: true` 加 `unavailable_reason: agent_refused`。客户端说明里 `complete` 的意思是"读到了保留内容的开头"、`unavailable_reason` 非空时数据只是旧尾部，两者分开表达，是 P59 的设计，不是缺陷；但并排读容易误会，用这个客户端的要先看 `unavailable_reason`。

再把文件改名放回去、调一次 `session.result`：`bytes_total 2510`、`source_bytes 2510`、`unavailable_reason` 为空，Operator 这时才建快照（`stdout.view` 2510 字节）——那次拒绝没有留下任何会被当成"完整"的东西。
