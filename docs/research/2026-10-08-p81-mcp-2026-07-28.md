## 2. 发现了什么、怎么修

规范 `server/utilities/caching`（2026-07-28）规定：`server/discover`、`tools/list`、`prompts/list` 的完整结果**必须**带 `ttlMs` 和 `cacheScope`。其中 `ttlMs: 0` 表示"马上过期，需要时可以每次都重拉"；字段缺失按 0 处理，并且"只应出现在旧版服务端"；`public` 表示"不含用户相关的数据，共享缓存可以转给任何人"。

修复前 ccnm 是这样的：

- **Runtime 的 `tools/list`**：照搬 rmcp 宏生成的值 `0` / `public`。代码注释原来写的理由是"整个连接期间不变，客户端可以一直留着"，跟这两个值在规范里的意思正好相反。而且工具表随读写模式变（read 会话不给写和执行那几个工具），会话有没有人值守也会影响 `_meta`，并不是对所有人都一样。
- **Runtime 的 `prompts/list`**：手写的 handler，两个字段都没带。
- **`ccnm_agent`**：两个列表都没带。
- **`server/discover`**：rmcp 默认给 `0` / `private`，本身是对的，没改。

**修法**：在 `crates/ccnm-core/src/mcp/mod.rs` 加 `cache_hints`、`TOOLS_TTL_MS`、`PROMPTS_TTL_MS`，四个列表 handler 都调它。只有协商版本 ≥ 2026-07-28 才填这两个字段：rmcp 只会替旧版本的 Host 去掉 `resultType`，不会去掉这两个字段，所以只能 handler 自己判断。取值和理由写在常量的注释里：

- 工具表 5 分钟：一个连接里不变；但 Host 可能把它带到下一个连接，`external_mcp` 改了之后表会不同。
- prompts 0：每次请求都重新扫 skills。
- 都是 `private`：列表属于这一个会话。

**prompts 为什么取 0 而不取正值**：先用 0 实测了一次。只要字段在，2.1.293 就只拉一次 `prompts/list`，引起反复重拉的是"字段缺失"，而不是"值为 0"。所以照实给 0，会话中途新加的 skill 下次请求就能看到。

## 3. 实测（夹具 `docs/research/probes/p81-mcp-2026-07-28.py`）

夹具的做法：

- **启动链路**：Claude Code 起一层只抄录、不改动的转发，记下每一条 JSON-RPC，再由它用 `env -i` 起 ccnm。
- **为什么要 `env -i`**：Claude Code 会把自己的环境（含 `ANTHROPIC_API_KEY`）带给 MCP server，ccnm 见到继承来的认证环境会按设计拒绝服务。第一次试跑三组都这样失败了，Claude Code 的 MCP 日志里写着 `CCNM_E_POLICY … authentication environment`。真实部署中间隔着 ssh，不会继承这些变量。
- **隔离**：Claude Code 的进程树套在 `sandbox-exec` 里，只允许连本机；HOME 是空临时目录。
- **工作区配置**：共用账号（P78），`external_mcp = "coding"`。

修复后的结果（`ccnm 0.13.0` 加本阶段改动）：

| Claude Code | 开场 → 协商到 | 第一次 `tools/call` | `prompts/list` 次数 | 取消送达 | sleep 存活（秒） |
| --- | --- | --- | --- | --- | --- |
| 2.1.286（sha256 `75e3016e…`） | `initialize` → 2025-11-25 | 0.18 s | 1 | 4.55 s | 0.82–4.48 |
| 2.1.293（sha256 `4e21122a…`） | `server/discover` → 2026-07-28 | 0.17 s | 1 | 4.52 s | 0.78–4.48 |
| 2.1.293 + `legacy` | `initialize` → 2025-11-25 | 0.18 s | 1 | 4.51 s | 0.79–4.48 |

表中时间都从 Claude Code 启动算起。sleep 存活时间是每 0.25 秒用 `ps` 采样得到的，所以"在取消送达后 0.25 秒内消失"只能精确到采样间隔。

**修复前**（同一套夹具，P81 改动之前的二进制）：

- 2.1.293 拿到 `tools/list` 的 `ttlMs: 0` / `cacheScope: public`，以及不带提示的 `prompts/list`。之后它在 0.16、0.41、0.92、1.92 秒共拉了四次 `prompts/list`，间隔按 0.25、0.5、1 秒翻倍，第一次 `tools/call` 推迟到 2.03 秒。
- 另两组走 `initialize`，各拉一次，第一次调用在 0.23 秒。
- 三组的取消同样送达、命令同样被停。所以兼容问题修复前就不存在，这次修的只是缓存提示。

**夹具自己踩过的两个坑**（已修，写在夹具注释里）：

- **instructions 的位置**：Claude Code 2.1.286 和 2.1.293 都把 MCP 的 instructions 放进 `messages[1]` 的 "MCP Server Instructions" 段，不在 `system` 字段，最初只查 `system` 会误报"没送到"。
- **`pgrep -f` 互相匹配**：并发的两个 `pgrep -f "sleep 27.381"` 会互相匹配到对方，凭空多出几个短命的 pid，看起来像命令被重起过。改用 `ps` 精确匹配整条命令行。
