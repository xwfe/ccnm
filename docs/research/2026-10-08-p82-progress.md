# P82 长命令跑着时给 Host 发进度（2026-10-08）

**证据范围**：离线测试（单元测试、真实二进制上的 Rust 集成测试与中立 Python 客户端），加上真实 Claude Code 2.1.286 和 2.1.293 二进制对着本机假模型的零额度实测（夹具沿用 [P81](2026-10-08-p81-mcp-2026-07-28.md) 的隔离办法）。**没有调用真实模型；没有经过真实 ssh 和 bridge；没有看 Claude Code 界面上实际怎么显示这些进度；没测 Codex；没有发版。**

## 1. 结论

| 验收 | 结果 | 依据 |
| --- | --- | --- |
| P82.1 前台 `exec_command` | 带 `progressToken` 时每 10 秒发一条 `notifications/progress`：`progress` 是秒数，`message` 是 `running for N s · <最后一行>`；10 秒内结束的不发；没 token 不发 | 第 2、3 节 |
| P82.2 `read_output` 等待 | 同样每 10 秒一条，`message` 是 `waited N s for r-… · <最后一行>` | 第 3 节 |
| P82.3 测试 | 8 个单元测试（最后一行的提取）；Rust 集成测试与中立 Python 客户端各一条，三个调用同时在跑，在旧代码上都红；真实 Claude Code 两版都接受 | 第 3、4 节 |
| P82.4 文档与门禁 | [协议文档 5.8 节](../protocol/remote-workspace-mcp-v1.md#58-进度通知p82-新增)（详细说明只放这一处）；门禁见 `status.json` | — |

## 2. 怎么做的

- **新模块** `crates/ccnm-core/src/mcp/progress.rs`：
  - `Reporter::for_call` 只在请求带 token 时才有值；
  - `Reporter::ticks` 从现在起 10 秒后第一次触发，错过的触发不补发；
  - `last_line` 从 run 目录里最近写过的那个流读末尾 4 KiB。
- **exec_command**：原来的 `select!` 只等两件事，命令结束、或者客户端取消；现在加了第三件事，就是这个定时器。命令的 run 目录在阻塞线程里才建出来，所以经 `exec::Running::run_dir`（一个 `OnceLock`）交给异步那一侧。
- **read_output**：等待部分同样处理。

**为什么是 10 秒**：Claude Code 自己的 `claude mcp serve` 每 30 秒报一次（CHANGELOG 2.1.271）。10 秒的话，一个人盯着编译时，在开始怀疑"是不是卡了"之前就能看到一条；每条经 ssh 只是一行短 JSON。

**最后一行怎么取**：
- 进度条靠 `\r` 重画，只留最后一帧；
- 去掉 `ESC [ … ` 颜色光标序列和 `ESC ] … BEL` 标题序列，其他控制字符换成空格，免得一条状态行去改 Host 的显示；
- 截到 120 个字符，按字符截，不会切坏多字节字符。

## 3. 实测（夹具 `docs/research/probes/p82-progress.py`）

假模型让 Claude Code 跑 `echo 'P82 step one'; sleep 25`（`timeout_ms` 60000）：

| Claude Code | 开场 | Host 给的 token | ccnm 发的进度（距第一条 MCP 消息） | 结果 |
| --- | --- | --- | --- | --- |
| 2.1.286 | `initialize` | `3` | 10.23 s `running for 10 s · P82 step one`；20.23 s `running for 20 s · P82 step one` | 正常返回（25015 ms），退出码 0，MCP 日志无错 |
| 2.1.293 | `server/discover`（2026-07-28） | `2` | 10.22 s、20.22 s，内容同上 | 正常返回（25020 ms），退出码 0 |

2.1.293 那次，Claude Code 的 MCP 日志里记了一行 ccnm 的 stderr：`WARN cannot list running mcp-serve processes; expired output is kept`。

- 它来自 server 启动时的过期输出清理（`retention::sweep_expired`）：问 `ps` 哪些 session 还有人服务，问不出来就什么都不删。
- 是有意的保守行为，和进度无关。
- 同一个夹具只在这一次见到，原因没查（`env -i` 加 `sandbox-exec` 环境下的 `ps` 偶尔失败？）。

## 4. 测试

- `progress::tests`（8 条）：
  - 最后一个非空行；
  - 没写过东西 / run 已经没了；
  - 最近写的流优先；
  - 进度条只留最后一帧；
  - 颜色、标题、控制字符；
  - 多字节字符上截断；
  - 1 MiB 输出只读尾部；
  - 两种 message 的格式。
- `external_mcp` 的 `a_call_waiting_on_a_command_reports_progress_on_its_token`：一个后台命令；再同时发三个调用：带 token 的前台 `exec_command`、带 token 的 `read_output` 等待、不带 token 的前台 `exec_command`。断言两个 token 各自收到格式正确的进度，并且所有进度都属于这两个 token。约 11 秒。旧代码上红：第一条断言就失败，一条进度都没有。
- 中立客户端 `tests/test_remote_workspace_mcp.py` 的同名用例：同样的三个调用，另外断言 `progress` 只增不减。旧代码上红：两个 token 都没收到进度。
  - 第一次跑时恰好用了被前面"旧代码红"那一步重编出来的旧二进制，也是红的。

## 5. 没做的

- `call_mcp_tool` 不转发远端 server 的进度。
- 钩子（P79）跑着时不报。它们最长 10 分钟，但一般很短；要报得先定"报的是谁的进度"。
- 没看 Claude Code 界面上实际怎么显示进度。官方文档说会显示，零额度的 print 模式看不到界面。
