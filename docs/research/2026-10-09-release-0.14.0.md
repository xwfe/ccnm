# 发版 v0.14.0，三台换装（2026-10-09）

用户 2026-10-09 在 P85 之后说"推送发版，并三机安装"。做法与 [v0.13.1](2026-10-08-release-0.13.1.md) 相同，这里只记不同的地方和结果。

## 1. 版本号

**0.14.0，次版本号**：P86 删了配置键 `codex_exec_server`，写着它的配置（哪怕是 `false`）解析失败，这是不兼容改动。P84、P85 只加不改。内部协议号没变（仍是 10），几台仍要一起升，两端版本号不同时 doctor 和起会话报 `CCNM_E_VERSION`。换装前核对过，三台的日用配置都没写这个键。

| 带了什么 | 记录 |
| --- | --- |
| P86 删掉封存的 Codex 原生执行链（`native/`、`internal exec-transport`/`exec-serve`、doctor 那一行，代码 +107/-6089） | `docs/plan/ROADMAP.md` P86、[双执行入口方案](../plan/runtime-surfaces.md)第 12 节 |
| P84 Linux 上 `mcp-serve` 是后代的 subreaper，会话结束时收掉 `setsid` 出去的后代再交写锁；macOS 不变（用户定不做） | [P84](2026-10-09-p84-linux-orphans.md) |
| P85 专用账号模式下 doctor 多一行"以你身份生效的文件" | [P85](2026-10-09-p85-opener-config.md) |

**第一次 CI 为什么红**：P52 的中立用例 `test_a_child_left_in_the_servers_process_group_ends_before_the_next_writer` 读 `child-tick` 时报 `FileNotFoundError`。用例只确认子进程"活着"就关会话，没等它开始写文件。runner 忙的时候，Python 子进程还没写第一笔就被正常收掉了。

这是测试赌时序，不是这一版的回归：
- 本机用后台优先级（`taskpolicy -b`）并发压测，新构建 24 次里 2 次复现；
- v0.13.1 的发布二进制 32 次里也有 2 次；
- 这条路径在 macOS 上从 v0.13.1 起没改过：中继、命令、进程模块一行没动，`server.rs` 只多了 P84 的清扫，而它在 macOS 上什么都不做。

修法是关会话前先等 `child-tick` 出现，断言不变。改完后同样压 24 次，不再出现。

**压测时还冒出一个差别，查清了**：同批 A/B 时，新版 16 次里有 4 次关会话超过 20 秒被强杀、4 次中继 server 没起来，v0.13.1 是 16/16。原因是新版用的是本地 debug 构建。换成 HEAD 的 release 构建，普通优先级、负载约 100，各跑 24 次：两边都是 24/24，用例耗时 1.10–2.07 秒，分布几乎一样。

## 3. 三台换装

照运维手册"用发布包升级"，不留备份。换之前三台都没有会话和 `mcp-serve`，fodelf 只有 Controller。传包和上次一样：fodelf 自己从 GitHub 下载；hpsrv 由本机 scp 给 root，再 chown 给 `ccrun`。

| | 本机（Runtime / Operator） | fodelf（Agent） | hpsrv `ccrun` |
| --- | --- | --- | --- |
| 之前 | v0.13.1 `15f01f13…` | 同左，Controller pid 3768 | v0.13.1 `b6200d31…` |
| 之后 | `ccnm 0.14.0`，`fd36fb2c…` | 同左；`controller install` 后 pid 52660，报 `listening: ccnm 0.14.0`，启动时刻比二进制修改时刻晚 1 秒 | `ccnm 0.14.0`，`f6806744…` |

四个日用 workspace（`ccnm`、`xdo`、`xshun`、`gld`）的 doctor 都是"可以用了（2 项不查）"、退出 0。上一版是 3 项不查，少的就是 P86 删掉的原生链那一行。Runtime、Agent、Controller、反向 SSH 都报 0.14.0。

## 4. 真机验证（零额度）

全程没有调用模型。

**P85，日用配置的 doctor**：日用配置写的是 `runtime_user = "bing"`，属于专用账号模式，所以出了这一行：

| workspace | 结果 |
| --- | --- |
| `ccnm`、`xdo`、`xshun` | "注意"，`present now: .claude` |
| `gld` | "正常"，`none present` |

和事先按目录内容推算的一致。

这次真机查出一处措辞问题：最后一句写"your git refuses this tree as another account's repository"。可日用配置里执行账号就是 `bing` 本人，git 并不拒绝，这句在这种配置下不成立。发版后在 main 上改成带条件的说法（"another account's git refuses…"，另加一句"若 bing 就是你自己的账号，这里不跨账号边界"），运维手册同步。**v0.14.0 里还是旧措辞**。

**P84，hpsrv 上的发布二进制**：用一个继承中立测试的小脚本，以 `ccrun` 身份跑两种逃逸。同一脚本换装前先对 v0.13.1 跑了一遍当对照：

| | v0.13.1（`b6200d31…`） | v0.14.0（`f6806744…`） |
| --- | --- | --- |
| 前台命令里 `setsid` 出去、不攥管道 | 会话结束后进程还活着，写锁 `released` | 进程没了，关会话 0.16 秒，`released` |
| 后台命令里 fork 后 `setsid`、攥着管道 | 服务端 20 秒内退不出来，被客户端强杀 | 进程没了，关会话 0.11 秒，`released` |

同机 `v0.14.0` 的 `tests.test_remote_workspace_mcp` 与 `tests.test_agent_skills` 用发布二进制跑：54 条全过（Python 3.14.8）。

**受管会话（P86 改过会话传输）**：
- 用日用配置跑 `ccnm run ccnm --detached`，由新 Controller 在 fodelf 上起 Claude Code，不发消息。状态是 `tools connected`。
- fodelf 上 Claude Code 的 MCP 日志里，`ccnm`（经 ssh 到本机 `mcp-serve`，1382 ms）和 `ccnm_agent`（42 ms）都报 `0.14.0`，都协商到 `2026-07-28`。
- 随后 `ccnm stop ccnm`：退出 0，本机 `mcp-serve` 没了，fodelf 没有 tmux 残留，`ccnm log ccnm` 第一行是"被停止"，四把写锁都是 `released`。
- 会话跑着时，`ccnm status ccnm` 的写锁那行报 `CCNM_E_CONFIG: asking the Runtime about its write guard needs an Agent instance binding`。这不是这一版引入的：v0.12.0 起就有，原因是日用 workspace 用的是旧写法 `agent_node = "agent"`，没有实例绑定。状态行自己也写明了"这不等于空闲"。

三台的临时文件（hpsrv 上 `ccrun` 家里的包与测试源码，本机临时目录）都已删掉。

## 5. 没验的

- **真实模型**：模型在 0.14.0 下怎么用工具，没验。
- **macOS 上 setsid 逃逸**：用户定不做，行为和 v0.13.1 相同。
- **P85 硬挡后 git 切分支、pull 会失败**：是推断，没实测；macOS 的 `chflags` 没测。
