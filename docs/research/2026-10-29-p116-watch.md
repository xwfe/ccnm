# P116：工具通道断了自动接回，通着的不动；attach 先接通再进（2026-10-29）

用户 2026-10-28 要"每次自动连接，已连接就不重连"，又定 attach 和 `ccnm <项目>` 一样先接通再进。怎么用写在[排错手册](../troubleshooting.md#tools-down--会话看着在跑模型却什么都够不着)，这里记查到了什么、改了什么、验到哪一步。

## 1. 先查：最近"MCP 没连上"是哪种

2026-10-28 读 AI 机器上 Claude Code 的 MCP 日志（`~/Library/Caches/claude-cli-nodejs/<工作目录>/mcp-logs-ccnm/`），10-18 起的全部 ccnm 日志。

- **每分钟一条的 `STDIO connection dropped after Ns uptime` 不是断开。** 它总跟着 `Dropped inbound request 'ping': not servable on this connection's protocol era`：Claude Code 丢掉 ccnm 的空闲 ping 时打的。uptime 一直在涨，后面的工具调用照常成功。
- 真正的断开只有 3 次，都在 shun 这个项目：
  - 10-21 02:15 UTC：AI 机器连不上项目机器（`ssh: connect to host xdwmbp port 22: Operation timed out`），45 分钟后才有下一次连接。这是 P116 自动接回要管的那种。
  - 10-23 12:26、10-24 13:45 UTC：两个连接在 2–3 秒内同时起来，都因为写锁被占（`workspace write guard is busy`）被拒。
- Claude Code 2.1.310 里"重启 stdio server"的文案只出现在协商协议那一步（`version negotiation probe … respawning`），会话中途断了它不会自己接回来。

**10-23、10-24 那两次是 Claude Code 的后台 agent（P116.4）。** 项目机器的 `ccnm log shun` 显示，10-24 13:45 UTC（本地 22:45，+09:00）落在 ccnm 会话 `44c3b067`（21:14 起，跑了 1 天）里。撞锁的两个连接的 Claude 会话 id `94d4c37f`、`4297dcf1` 不是任何 ccnm 会话。AI 机器上 `94d4c37f` 的转录元数据（只看字段，没读内容）是 `sessionKind: "bg"`、`agentName: "界面文字精简与功能提示"`；10-23 那次的 `15e14ecb` 也有 `agentName`。所以是后台 agent 另起了进程，加载同一份 MCP 配置，开了第二条 ccnm 通道，撞上了一个项目一个写入者的锁。

ccnm 没有错：单写锁就是为这个设计的。2.1.310 里有 `CLAUDE_CODE_DISABLE_AGENT_VIEW`、`CLAUDE_CODE_DISABLE_BACKGROUND_TASKS` 两个环境变量和设置项 `disableBackgroundAgentLaunch`，哪个能挡住后台 agent 没有实测。用户在用这个功能，关不关、或者给后台 agent 只读的工具，留给用户定；排错手册先加一节说明原因和现在的做法。

## 2. 改了什么

**会话跑着时自动接回**（`work::watch_tools`，Controller 起的一个线程，每 30 秒一轮）：

- 列出这台机器 tmux 里的受管会话。没有远端通道的（同机）和 Codex 会话跳过，Codex 没法重连正在跑的会话（P96）。
- 每个会话先看通道进程在不在（`ccnm status` 用的同一个 `ps`）。通着就不做别的；之前记下的"没接上"清掉。
- 断了：之前失败过、又还没到下次该试的时间，就什么都不做。到时间了，就走 P100 进会话时的同一段 `reconnect_down`：先问项目机器（版本、项目目录、`runtime-audit`），问得通、输入框是空的，才敲 `/mcp reconnect ccnm`，最多等 20 秒。
- 结果记在会话目录的 `reconnects.json`：
  - 接回了：次数加 1，记下时间。
  - 项目机器问不通、或敲了没接上：退避 30 秒、1 分钟、2 分钟，之后每 5 分钟一次，一直到会话结束。
  - 输入框里有字：30 秒后再看，不算失败、不加退避。
- 每次接上、没接上，Controller 日志里各打一行。一轮 panic 了也只记一行，下一轮照常跑。

**一次只有一个人在接**：新加 `reconnect.lock`（会话目录里，flock）。巡检拿不到锁就跳过这个会话；人进会话（P100）时拿不到就等，等到了先再看一次通没通，通了就不敲。用单独的锁文件，不借 P58 的 `control.lock`：重连最多 20 秒，借用会让 `ccnm stop` 跟着干等。

**`ccnm status` 的工具那一行**：接回过就写"通（断过，自动接回过 N 次，最近一次：… 前）"；断着、Controller 还在试时，多一行"Controller 在自动接：上一次没接上（原因），… 后再试"。信息在 `LiveSession` 新加的可选字段 `reconnects` 里。这个结构没有 `deny_unknown_fields`，旧的项目机器读得了。

**attach 先接通再进**（P116.3）：`ccnm attach` 先发一个新的内部请求 `agent-attach-check`，在 AI 机器上做 P100 那一步，结果带回项目机器、用人的语言说，再交出终端。接不上就不让进，报错写原因和 `ccnm attach <项目> --force`。在 AI 机器上直接敲 `attach` 时在本地查。这样拆开，是因为交出终端的那条 `ssh -t` 带不回结构化的结果，AI 机器也不知道人用哪种语言。AI 机器是 v0.21.1 或更早、不认识这个请求时，照旧直接进，并打一行说明。

P100 的那段因此拆成两段：`tools_on_entry`（先看通没通）和 `reconnect_down`（看到断了之后怎么接）。拨项目机器改用会话自己记下的链接（`dial_link`），不再用项目机器给的节点名：老写法的会话里只存着链接。P100 那两条"不管工具先进去看：`ccnm attach`"的退路说法，也改成了 `--force`。

## 3. 离线验证

本机 macOS arm64：

- 巡检单元测试 5 条（用 P100 的假 runner，按顺序喂 tmux、ps、ssh 的输出）：
  - 通着：只跑一次 `ps`，并清掉旧的"没接上"。
  - 项目机器连不上：连续 5 次失败，下次时间依次是 +30、+60、+120、+300、+300 秒；没到时间那轮只跑一次 `ps`，什么都不敲。
  - 断了、项目机器通、输入框空：敲了重连，次数记 1。
  - 输入框有草稿：不敲，30 秒后再看，失败次数还是 0。
  - 别人拿着重连锁：只跑一次 `ps` 就让开。
- attach 检查单元测试 3 条：通着时没话说；断了又连不上项目机器时，报错里有原因和 `ccnm attach xshun --force`，退出码 21；没有会话时报没有会话。
- status 一条：接回过和正在接两种说法，第二种是单独一行、和上面对齐。
- CLI 集成 2 条（假 ssh）：`ccnm attach` 在 AI 机器说接不上时，退出码 21、报错带 `--force`，终端没交出去；加 `--force` 就交了。AI 机器不认识这个检查时，打"太旧"，照样进。
- P100 原有的 `work` 测试全部照旧通过。拆成两段时我先在拿锁之后多查了一次 `ps`，把 P100 测试喂的假输出全打乱了，改成只有真的等过锁才重查。

门禁见第 6 节。先在旧代码上红：这些测试测的都是新函数和新请求（`watch_one`、`attach_check`、`agent-attach-check`、`reconnects`），在旧代码上编译不过；没有单独 stash 再跑一遍。

## 4. 真机（2026-10-29，零额度）

用户同意在项目机器（本机）和日常用的 AI 机器上换这一版：`0d644fe` 的发布构建（sha256 `da2845d3…`，版本号仍是 0.21.1），AI 机器上 `ccnm controller install` 重启了 Controller。AI 机器上用户开着的三个会话没停，只换文件。Claude Code 是 2.1.312。

**换上就用上了。** Controller 起来后 34 秒、40 秒，把用户两个工具断了好几天的会话（keex 跑了 13 天，xdo 跑了 15 天）接了回来：界面上是 `/mcp reconnect ccnm` 和 `Successfully reconnected to ccnm`，项目机器上各起了一个新的 `mcp-serve`，`ccnm status` 写"通（断过，自动接回过 1 次…）"。另一个工具通着、有人接着的会话（ragcheck）没被碰，它的 `mcp-serve` 还是换装前那个。

**怎么只断一个测试会话。** 不动防火墙，这个对话和用户的会话也不受影响：

1. 在没开会话的 `ccnm` 项目上起测试会话（`ccnm run ccnm --detached`）。
2. AI 机器的 `~/.ssh/config` 临时加一个别名 `ccnm-p116`（先备份）。它和日常连项目机器的那条一样，只多一个 `ProxyCommand`：一个小脚本，平时就是 `nc` 到项目机器，一个连接一个进程；有标记文件时等 10 秒后失败，像网断了。
3. 只改这个测试会话的 `session.json`，把记下的项目机器别名换成 `ccnm-p116`，再杀掉它的通道进程。之后它的通道和 Controller 替它拨的号都走这个转发。

**结果。** 时间从开始断网算起：

| 时刻 | 做了什么 | 看到什么 |
| --- | --- | --- |
| −68 s | 杀掉测试会话的通道进程，项目机器是通的 | 32 秒后 Controller 经 `ccnm-p116` 接回来，次数 1 |
| 0 s | 新连接开始失败；正在用的那个转发冻住（`SIGSTOP`） | `ccnm status` 仍是"通"：进程还在，只是包不走（见第 5 节） |
| 60 s | 杀掉冻住的转发。10-16 实测内核在 100–200 秒放弃死连接，这里取 60 秒 | 8 秒后 status 变成"断了" |
| 95 s | Controller 第一次试 | 没接上：`ssh ccnm-p116: Connection timed out during banner exchange`，30 秒后再试。status 多出一行"Controller 在自动接：上一次没接上（…），不到 1 分钟后再试" |
| 135 s | 第二次 | 同样没接上，下次 1 分钟后 |
| 180 s | 网络恢复 | |
| 201 s | 第三次 | 接上，次数 2。**恢复后 21 秒** |

接着又测了 attach：再断一次，这时项目机器也连不上，敲 `ccnm attach ccnm`。11 秒后被拒，退出码 21，报错写着原因和 `ccnm attach ccnm --force`。放开后 8 秒，Controller 接回，次数 3。

几处旁证：

- 每次断开，项目机器上旧的 `mcp-serve` 都退出了：转发被杀，sshd 看到连接关闭。所以接回时写锁是空的，最后只剩新起的那一个。
- Claude Code 的 MCP 日志里有三条 `Connection established`。
- 会话转录里只有三次本地的 `/mcp` 命令，没有一条 assistant：全程没调模型。

**收尾。** 测试会话已经 `ccnm stop`，`session.json` 换回原样；`~/.ssh/config` 用备份恢复，`cmp` 一致，删了备份；临时目录和两个兜底 `sleep` 也都删了、杀了。两台都留着这一版：用户要用自动接回。

**真机上看出来、改了的两处文字（装上的构建里还没有）：**

- "最近一次在 不到 1 分钟前"多一个空格，改成"最近一次：不到 1 分钟前"。
- Controller 正在试时，工具那一行还写"断了——在 Claude 里：/mcp → ccnm → Reconnect"，和下一行矛盾：手动接也一样连不上。改成只写"断了"。输入框里有草稿那种情况还得人动手，所以照旧给手动的写法。

## 5. 没验的

- **冻住时看不出断了。** 巡检和 `ccnm status` 只看通道进程在不在。连接冻住时进程还在，要等内核放弃连接（10-16 实测 100–200 秒）才看得出来。所以真断网时，从断网到开始接最多多出约 3 分钟。这是 P116.1 定下的做法，没改。
- 真关 Wi-Fi、笔记本睡着：没做，用别名上的转发模拟的。
- 项目机器那头旧的 `mcp-serve` 还没退，重连就来了：会撞写锁，按失败退避再试。这种情况没模拟。
- `attach --force` 的真机：要终端，只有离线测试。
- 后台 agent 的几个开关：没测哪个管用（见第 1 节）。
