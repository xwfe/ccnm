# Phase 1B 实测记录：one persistent SSH stdio MCP（2026-09-03）

这份文档回答一个问题：**工作机 Claude → 一条 SSH → 家庭机 ccnm MCP server**，是不是真的只有一条连接、
一个进程，每次工具调用的代价是不是一个网络往返。答案是：是，数据在下面。

环境：

```text
家庭机   fodelf 的 Mac mini（arm64, macOS 26 / Darwin 25.3），ccnm 0.1.0 在 ~/.local/bin/ccnm
工作机   xdwmbp（arm64, Darwin 25.6），用户 bing，ccnm 0.1.0 在 ~/.local/bin/ccnm，Claude Code 2.1.259
网络     Tailscale direct（不走 DERP），ping 平均 17.5 ms
alias    家庭机 → 工作机: xdwmbp        工作机 → 家庭机: fodelf
```

两台机器上的 ccnm 由 `cargo build --release` 后手工 `cp` / `scp` 安装，同一次构建（commit 59b42fd）。

## 1. Rust MCP SDK 选型：rmcp 3.2.0

candidates 里只有 `rmcp`（modelcontextprotocol/rust-sdk 官方）是活跃维护、协议版本跟得上的。实测：

```text
features        server, macros, transport-io, client, transport-child-process（default-features = false）
tokio           rt, io-std, process, time（current_thread runtime，只在 crates/ccnm-core/src/mcp 里）
依赖数          server 单独 68 个 crate；server + client 78 个
重依赖          tokio、futures、serde_json、schemars；没有 hyper / reqwest / axum / rustls
release 二进制  单独的 srv 示例 2.4 MB（strip 后）
```

契合度检查（都在 rmcp 3.2.0 源码里核实过）：

```text
stdio                     rmcp::transport::stdio()
initialize.instructions   ServerInfo::with_instructions
tools/list, tools/call    #[tool_router] / #[tool] / #[tool_handler]
structuredContent         CallToolResult::structured(value)，content 可覆盖成人话
cancellation              RequestContext::ct（CancellationToken），notifications/cancelled 会触发
stdin EOF 退出            service.waiting() 在 stdin 关闭时返回 QuitReason
client + 子进程 transport TokioChildProcess::builder(cmd).stderr(piped).spawn()
优雅关闭                  transport.close() 关 stdin → 等子进程退出 → 超时才 kill
```

候选对比（subagent 用 `cargo info` 查的，2026-09-03）：rmcp 3.2.0 官方、2026-08-31 发布、MSRV 1.88、近期下载
1200 万；rust-mcp-sdk 2.0.0 活跃但 default feature 拉 auth / sse / reqwest / jsonwebtoken；mcp-core、mcp-server、mcp-sdk、
mcp_rust_sdk 都停更一年以上。没有第二个选择。

坑（都踩过）：

```text
1. #[tool_handler] 宏展开出 Result<_, ErrorData>，和 crate 里 pub type Result<T> 别名撞名；server.rs 不 import 那个别名
2. client 侧 InitializeResult.server_info 是 Option<Implementation>，不能直接取字段
3. CallToolResult / InitializeResult / CallToolRequestParams 都是 #[non_exhaustive]，只能走构造函数，字段可以事后赋值
4. 项目里如果有 schemars 0.8，报 "the trait bound A: rmcp::schemars::JsonSchema is not satisfied"，看着像 derive 没生效，
   实际是两个 schemars 并存。ccnm 不声明 schemars；以后工具要参数就用 rmcp::schemars + #[schemars(crate = "rmcp::schemars")]
5. chrono 是 rmcp 的无条件依赖，去不掉
6. TokioChildProcess 的 Drop 靠 tokio::spawn 去 kill 子进程，runtime 先关就可能漏；ccnm 的 probe 走 client.cancel()
   → transport.close() → graceful_shutdown()（关 stdin → 等退出 → 超时 kill），不依赖 Drop
7. 用 () 当 ClientHandler 协商出的协议版本是 2025-11-25；手工发 2025-06-18 也能协商
8. stdout 噪音没有传说中致命：rmcp 3.2.0 对解析不了的行静默跳过（transport/async_rw.rs:170，对齐其它官方 SDK，issue #938）。
   subagent 拿一个先打印 4 行 MOTD 再 exec server 的脚本当 transport，client 正常。对 ccnm 的意义：家庭机 sshd 的 banner /
   MOTD 不会炸掉 MCP。但格式对、结构不对的 JSON 会触发 Invalid Request 错误响应，规矩仍是：stdout 只放 MCP，日志走 stderr
```

体量（subagent 在同一台机器实测，和上面我的 `cargo tree` 口径略有不同）：仅 server 56 个 crate，server+client 63 个，
加上 clap/toml 的 ccnm 形态 82 个；对照只有 clap+serde+toml 是 27 个。release 二进制从 0.73 MB 涨到 4.47 MB；clean release
构建从 9 s 涨到 28 s。

结论：作为"小而透明"的依赖可以接受，"小"要打折扣（依赖数翻两倍、体积 +1.7 MB）。手写 JSON-RPC server 侧大概 300 行，但要自己扛
协议版本协商、cancellation、schema、以后的 spec 变更，不值得。整个 binary 只有 `mcp/` 是 async，`main` 仍然是同步的。

## 2. MCP initialize / tools/list / tools/call 实际报文

本机直接对 `ccnm internal mcp-serve --payload <TOKEN>` 的 stdin 灌 JSON-RPC 抓的，逐行：

请求：

```text
156 B  {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"raw-capture","version":"0"}}}
 46 B  {"jsonrpc":"2.0","id":2,"method":"tools/list"}
 96 B  {"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"workspace_info","arguments":{}}}
```

响应：

```text
364 B  {"jsonrpc":"2.0","id":1,"result":{"protocolVersion":"2025-06-18","capabilities":{"tools":{}},"serverInfo":{"name":"ccnm","version":"0.1.0"},"instructions":"CCNM remote workspace \"xshun\". The project lives on another machine and is reachable only through the ccnm tools; there is no local copy. Every path you pass or receive is relative to the workspace root."}}
264 B  {"jsonrpc":"2.0","id":2,"result":{"tools":[{"name":"workspace_info","description":"Name, git status and platform of the remote workspace. Call once to orient; all other tool paths are relative to this workspace.","inputSchema":{"properties":{},"type":"object"}}]}}
293 B  {"jsonrpc":"2.0","id":3,"result":{"content":[{"type":"text","text":"workspace xshun (git repository root, macos/aarch64); all paths are relative to its root"}],"structuredContent":{"calls_served":1,"git":true,"platform":"macos/aarch64","server_pid":78540,"workspace":"xshun"},"isError":false}}
```

`tools/list` 的 result 用 rmcp client 重新序列化是 230 B（probe 报告里的 `tools_list_bytes`）。7 个工具的
16 KiB 预算，现在 1 个工具用了 230 B。

instructions 203 B。stderr 空：server 没往 stdout 写过任何非 MCP 的东西。

## 4. 100 次 workspace_info：work → one ssh → home

命令（家庭机上跑，它 ssh 到工作机，让工作机 ssh 回来做 MCP）：

```bash
ccnm mcp probe xshun --calls 100
```

结果：

```text
initialize in 275 ms, tools/list (1 tool, 230 B), workspace_info x100 p50 18 ms p95 22 ms max 153 ms, pid 77912 throughout
{"connect_us":275463,"server_name":"ccnm","server_version":"0.1.0","instructions_bytes":203,
 "tools":["workspace_info"],"tools_list_bytes":230,"calls":100,
 "call_p50_us":18080,"call_p95_us":22323,"call_max_us":153972,"server_pid":77912,"single_process":true}
整条命令 3.44 s（含家庭机 → 工作机那一跳）
```

同一段时间在两台机器上每 50 ms 采样一次进程（pgrep 模式写成 `mcp-serv[e]` 避免匹配到采样 shell 自己）：

```text
家庭机  ccnm internal mcp-serve      pid 77911（sshd 起的登录 shell）、77912（ccnm 本身），各 14 个采样，
                                      从头到尾就这两个
工作机  ssh … internal mcp-serve     pid 27188，29 个采样，从头到尾就这一个
probe 结束后两边 pgrep 都是空：server 被正常收掉，没有残留
```

in-band 证据：100 次调用返回的 `server_pid` 全部是 77912，`calls_served` 1 → 100 单调递增，所以
`single_process = true`。

initialize in 51 ms, workspace_info x100 p50 0.075 ms p95 0.115 ms max 0.381 ms, pid 78527 throughout

## 6. 数据放在一起看

```text
                       local stdio     SSH stdio       差值
initialize             51 ms           275–347 ms      ≈ 一次 ssh 冷连接（裸 ssh true 实测 330–450 ms）
workspace_info p50     0.075 ms        18 ms           ≈ 一个 RTT（ping 17.5 ms）
workspace_info p95     0.115 ms        22 ms
workspace_info max     0.38 ms         154 ms          单次抖动，100 次里一次
```

第 27 节的 latency gate 说"remote overhead ≈ 一个 SSH stdio round trip + serialization"：p50 18 ms 对
17.5 ms 的 RTT，序列化开销在 1 ms 以内。UX 门禁 "> 250 ms 额外 transport delay" 只在冷连接那一次出现，
之后没有。
