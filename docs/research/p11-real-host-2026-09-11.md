# P11.3 真机记录：真实 MCP Host 上的允许矩阵（2026-09-11）

这一轮做的是 P11 剩下的那半边：把 Remote Workspace MCP 放到**真的 ssh、真的隔离执行身份、真的 Claude Code** 上跑一遍。前面 P11.1／P11.2／P11.4 是离线证的（[跨入口记录](cross-entry-p11-2026-09-11.md)），离线证不了的只有这一条。

机器可判的部分写在 [p11-matrix-20260911.json](p11-matrix-20260911.json)，退出码 0。人要看的部分写在下面。

### 允许矩阵（脚本判的，没有模型参与）

`scripts/p11_matrix_check.py` 从 Host 拨真 ssh 过去，判据全是 Runtime 侧副作用：

- coding 腿七个工具；`apply_patch` 真写了一个带一次性 token 的文件；
- 用 `exec_command` 在那台机器上 `stat` 它，**属主是 `ccrun`**；同一条腿 `id -un` 也是 `ccrun`——外部入口最终落在同一条隔离执行链上，不是别的身份；
- read 腿正好四个工具，读到同一个 token（两个入口同一棵树）；
- read 腿按名字硬调三个没给的工具，**参数全部合法**，三次都是 `CCNM_E_POLICY: <tool> is not available: this workspace is open for external MCP in read mode`；
- 同一棵树的第二个 coding 起不来，写锁拒绝；
- `p11read`（只配了 read）上请求 coding：`workspace p11read allows external MCP in read mode; coding was requested`——拒绝，不降级；
- Host 看到的全部文本扫私有标记（`.claude`、`auth.json`、`id_ed25519`、`authorized_keys` 等）：干净；
- 产物删除并确认它没了。

### 真实 Claude Code：read 模式

让它列目录、读文件、然后建一个文件。前两件成了，第三件**它连试都没试**，原话：

> ccnm-read 这个 server 一共只暴露 4 个工具：`list_files`、`read_file`、`search_text`、`workspace_info`。全是只读的……这次不是「调了一下被服务端拒绝、拿回一条报错」，而是这个动作在工具层面就不存在入口——请求根本发不出去。

它还明确说了不拿本地 Write 工具顶包，因为那只会造出一个假的「成功」。

Runtime 侧复核：`claude-wrote-this.txt` **不存在**。

这比计划里预期的更强，但要说清楚它证明的是**另一件事**：真实 Host 在 read 模式下压根拿不到写工具，所以没有"调用被拒"这一步。"忽略 annotations 硬调也被拒"那条由矩阵脚本证（它按名字硬调、参数合法），不能拿这一段冒充。

## 三、真机才暴露的问题（一）：`~/.config/ccnm` 里放个备份，exec 就被拒

第一次跑矩阵，链路一路走到 `exec_command` 被拒：

```
CCNM_E_POLICY: the runtime is running as ccrun and is not confined, so exec_command is refused:
  - No SSH keys: a possible private SSH key is accessible or unknown (names and contents withheld)
```

ccrun 的 `~/.ssh` 里只有 `authorized_keys`、`config`、`known_hosts`，一把私钥都没有。真正的原因是**十分钟前我自己放进去的一个备份**：`~/.config/ccnm/config.toml.pre-p11`。

凭据审计检查两个目录：`~/.ssh` 和 `~/.config/ccnm`（第二个是 P7.3 加的，因为当时有人把传输密钥从 `~/.ssh` 搬到那里，这一行就绿了——`mv` 一下就能满足的检查不是检查）。白名单只放行 `*.pub`、`*.toml`、`known_hosts`、`known_hosts.old`、`config`、`authorized_keys`、`authorized_keys2`。`config.toml.pre-p11` 不以 `.toml` 结尾，于是被当成"可能的私钥"。

**行为本身是对的**（fail-closed：一个叫 `config.toml.pre-p11` 的文件确实可能是私钥），**但那句话把人指错了地方**——它说 SSH key，实际是"这里有个我排除不掉的文件"。任何人把 `config.toml.bak`、`config.toml~`、编辑器备份留在那个目录里都会踩到，而且现象是 exec 被拒、理由是 SSH 密钥。

已写进[出错了怎么办](../troubleshooting.md)。P7 那轮的备份放在家目录根下（`config.toml.pre-p7codex`），现在知道那不是巧合。

**修法是把备份挪出那个目录，不是开 `allow_unconfined_exec`。** 后者会把要验的东西绕过去。

## 四、真机才暴露的问题（二）：启动失败的诊断到不了人眼前

契约规定启动失败 = 退出码 ≥1 + stderr 第一行 `CCNM_E_*`。手工跑一个没 opt-in 的 workspace，诊断确实在：

```
$ ccnm mcp bridge p7dogfood --node runtime --mode read
CCNM_E_POLICY:
workspace p7dogfood is not available to external MCP
退出码 33
```

把同一个 server 配给真实 Claude Code，它显示的是**全部**：

> The following MCP servers are configured but failed to connect — their tools (typically named mcp__<server>__*) are unavailable for this session:
> ccnm-closed (CONNECTION_CLOSED): "Connection closed"

`CCNM_E_POLICY` 那一行、"workspace 没有开放给外部 MCP" 那一句，**一个字都没到用户面前**。

这不是 ccnm 能单方面修好的：Host 怎么处理子进程的 stderr 是 Host 的事。能做的是把它写进文档——看到 `Connection closed` 就手工跑一遍 bridge 命令，理由在 stderr 上。已加进[出错了怎么办](../troubleshooting.md)。

契约那句"启动失败对人可见"因此要读作**对着终端跑的人可见**，不是"对 Host 里的用户可见"。

## 六、这一轮不覆盖什么

- **只有 macOS。** 两端都是 macOS，Linux Runtime 是 P12。
- **只有一个 Host、一个版本。** Claude Code 2.1.268，`-p` 打印模式加 `--mcp-config --strict-mcp-config`；没验交互式 UI 怎么显示，也没验 Codex 或别的 MCP Host。
- **只有一棵一次性空树。** 远端真实项目的长时 dogfood 是 P12.1。
- **egress 不作声明。** 这一轮没碰网络策略。
- **证据文件里的写锁拒绝措辞是修之前的。** `another managed session still owns this working tree` 与契约 fixture 对不上（fixture 里没有 `managed`），已在 commit `8c27aa5` 改成 `another session`；部署的二进制早于该提交，所以 JSON 里留的是旧文案。两者只差这一个词，不影响任何判据。
