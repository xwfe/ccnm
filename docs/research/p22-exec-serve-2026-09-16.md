# Runtime 侧受管 exec-server（P22，2026-09-16）

设计见[双执行入口方案](../plan/runtime-surfaces.md)第 12 节，规则表见 [P21 记录](p21-codex-native-surface-2026-09-16.md)，验收见 ROADMAP 的 P22。本阶段只做 Runtime 这一半：`ccnm internal exec-serve`。Agent 侧还没有东西会连它，Codex 的启动参数一行没改。

## 做了什么

Runtime 上多了一个内部命令 `ccnm internal exec-serve --payload <base64url>`，wire protocol 是 **6**。它依次做这几步：

1. **打开**：按 Runtime 自己的配置解析 workspace、root 和 Codex 二进制。请求里只有 workspace 名、Agent 身份和 session id；带 `root` 或 `codex_bin` 字段的请求解码就失败。需要同时满足三条：workspace 写了 `codex_exec_server = true`，Runtime node 写了 `codex_bin`，Agent 是 Codex。
2. **审计**：和 MCP server 用同一个 `ExecGate`。`process/start` 就是换了名字的 `exec_command`，所以要的许可也一样：没确认隔离、也没写 `allow_unconfined_exec`，就拒绝。
3. **版本**：`codex_bin --version` 必须是 `codex-cli 0.154.0`，而且在拿锁之前核对。
4. **写锁**：和 `mcp-serve` 同一把锁。
5. **启动**：以子进程起 `codex exec-server --listen stdio`，并放进单独的进程组。不用 `exec` 替换自己，否则 Drop 不会跑，锁会永远是 `held`。
6. **转发**：客户端发来的每一行先过 `native::policy`，再决定转给 exec-server、由 ccnm 直接回答，还是丢弃。exec-server 的输出按整行转回客户端。
7. **关闭**：关掉 exec-server 的 stdin，等它退出，再**按环境变量标记扫进程表**。扫干净了才放锁，扫不干净就让锁保持 `held`。

## 开工前的一条新实测：为什么要扫进程表

本机 Codex 0.154.0，stdio，脚本只在本轮临时用，没有入库：

| 命令 | 进程组 | 关 stdin 后 |
| --- | --- | --- |
| `sh -c 'exec sleep'`（管道） | 自己一组，不是 exec-server 那组 | 被清掉 |
| 同上，`tty: true` | 自己一组 | 被清掉 |
| `sh -c 'sleep & echo'`（后台） | sh 那组，父进程变成 1 | 被清掉 |
| fork 后 `setsid` 再 `exec sleep` | 自己的会话，父进程 1 | **活下来** |

exec-server 在 0.01 秒内退出。所以"杀掉 exec-server 的进程组"一个命令都够不着，而"信 exec-server 自己清理"会漏掉 `setsid` 的那种。另一个事实是：`envPolicy.inherit` 为 `all` 时，所有子进程都带着 exec-server 的环境变量，`ps -E` 看得到（上表 4 个进程都看到了标记）。

于是监督进程给 exec-server 加一个 `CCNM_EXEC_SESSION=<session>-<随机 UUID>` 变量，关闭时找带这个值的进程：找到就杀，再查一遍，最多等 5 秒。macOS 用 `ps -axEww`，Linux 读 `/proc/<pid>/environ`。列不出进程表、杀了还在，都算"证明不了"，这时锁留在 `held`，报错里带着这个标记值，恢复步骤写进了[运维手册](../operations.md)。

**规则表因此补了一条**：`process/start` 的 `envPolicy.inherit` 必须是 `all`，`includeOnly` 必须为空，`exclude`、`set` 和 `env` 里都不能出现这个变量。Codex 自己发的请求本来就满足。

**防不住的情况**：命令自己清空环境变量再脱离会话，就找不到它。这属于计划里单独列出的平台隔离边界，监督进程关不上这个口子。

## 相对 P21 规则表和 ROADMAP 的调整

| 条目 | 调整 | 原因 |
| --- | --- | --- |
| P22.3 "环境按白名单构造" | 改为和 MCP `exec_command` **同一套**子进程环境：`runtime_child` 清掉 Agent 私有变量、认证类变量和 `SSH_AUTH_SOCK`，再设 ccnm 生成的 `CODEX_HOME` 和会话标记 | 计划要求原生链和 MCP 受同样约束，单给原生链一套白名单，两个入口里命令看到的环境就不一样。另外，带认证类变量的 Runtime 环境在审计阶段就整会话拒绝（集成测试里设了 `SSH_AUTH_SOCK`，会话直接起不来），不会走到清理这一步 |
| 规则表 `process/start` | 加上会话标记的要求 | 见上一节 |
| 规则表 `process/start` | `shellSnapshot`、`networkProxy` 必须为空 | 协议里有这两个字段，P21 没见过；按"没测过就不开"处理 |
| 规则表 sandbox | `temporaryDirectories` 必须为空；出现未知字段就拒；`missing_path_behavior` 只接受 `skip` | `tmpdir` 条目按 `temporaryDirectories` 解析，由客户端填的话，一条临时目录写权限就能指向任何地方 |
| 规则表文件写 | 不能写 `.git`，不能写穿 symlink，不能删工作区根 | 直接用 MCP `apply_patch` 的 `resolve_write`，同一契约 |
| 规则表文件读 | 新增 `resolve_inside`：包含判断和 `resolve_read` 一样，但**不存在的路径放行**，指向不存在目标的 symlink 拒绝 | Codex 靠 exec-server 自己的 `-32004` 去探 `AGENTS.md` 和新文件 |
| P21 待测项"句柄是否按连接隔离" | 不再需要 | 每个会话一个监督进程、一个 exec-server 进程，句柄跨不了会话 |
| 单帧上限 | 客户端单条消息最多 32 MiB，超过就结束会话 | 比 exec-server 的 64 MiB 小，由 ccnm 说明原因（写在 stderr）。Codex 每次 `fs/writeFile` 发整个文件，所以这也是这条链能写的最大文件 |

## 测试

- `native::serve`：5 个。包括超长行、版本门、执行环境，以及**真实起一个带标记的 `sleep`**，验证扫描能找到它、杀掉它、再报告干净；另有列不出进程表或杀不掉时绝不报告干净的用例。
- `runtime`：新增 3 个。`open_native` 的各种拒绝；请求里带 `root` 或 `codex_bin` 无法解码；`mcp-serve` 不接受 protocol 6。
- `mcp::path`：新增 1 个，测 `resolve_inside`。

**集成测试** `crates/ccnm-cli/tests/exec_serve.rs`，9 个，全部通过真实二进制。执行端是 `tests/fixtures/fake_exec_server.py`：它完全无视沙箱，真的写文件、起进程。所以"被 ccnm 拒绝"要靠磁盘上没有文件、它的日志里没有这条请求来证明，而不是看回包。这个客户端发的是原始 JSON，没有复用 ccnm 的规则代码，只借 ccnm 的类型编码启动载荷（和 `runtime_open.rs` 一样）。

**接真 exec-server**（`CCNM_TEST_CODEX_BIN=/opt/homebrew/bin/codex`，codex-cli 0.154.0，macOS 26.6.2 arm64）：工作区内的命令成功；同一条命令里往工作区外写，被 exec-server 自己的 Seatbelt 沙箱拒绝（`Operation not permitted`，从它的 `process/output` 里看到）；`sandbox: null` 的提权命令和批准后的越界写由 ccnm 拒绝，都没落盘；带 sandbox 的写文件成功。过程中顺带知道了两件事：真 exec-server 要求 `metadata.threadId` 是 UUID（fixture 里被脱敏成了占位符，真机那组测试去掉了这个可选字段）；它会穿插发 `process/output` 通知，测试客户端要跳过这些通知再等回复。

**测试抓到的一个真 bug**：转发 exec-server 输出的线程先拿 stdout 锁，再阻塞等下一行。exec-server 在客户端发下一个请求之前没话说，而客户端在等 ccnm 的拒绝，ccnm 的拒绝又要这把锁，于是死锁。改成先等到数据再拿锁。

## 没做到、没测到的

- **Linux 那一路只在 CI 上跑过。**`/proc/<pid>/environ` 那个分支本机测不到。推送后 GitHub Actions 的 `linux-runtime` 任务（ubuntu-24.04，run 35089629254）Clippy 和 Test 都通过，`exec_serve` 的 9 个集成测试随 `cargo test --workspace` 在那里跑过；日志要登录才能读，这里只记结论。
- **静默断开的 SSH。**`mcp-serve` 靠 MCP ping 发现"对面没了但 FIN 丢了"的连接；exec-server 的协议里没有能主动发给 Codex 的 ping，所以这种情况下监督进程会一直等 stdin、一直占着锁。留给 P24 做真机故障测试，看 Agent 侧 SSH 的保活能不能兜住。
- 真 exec-server 只在 macOS 上接过。Linux 上真 exec-server 加监督进程这个组合没测，P21 只测过容器里的 exec-server。
- 进程扫描只能防住保留了环境变量的进程，清空环境再脱离的不在范围内（见上文）。
- exec-server 的 stderr 原样交给监督进程的 stderr，也就是 SSH 的 stderr；内容里会有工作区路径。
- 没有 Agent 侧，没有真实 Codex 会话，没有部署，没耗额度。
