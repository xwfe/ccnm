# P7.4 Batch E：新身份链在真机上跑通了（2026-09-10）

P7.4 把身份和控制链改了四批半（A、B、C、D、D2），全是离线验证。这一轮把新链路放到 P7.3 那套真机拓扑上跑一次最小复验：**通过**。

不是重跑 P7.3 的完整 dogfood——那次是"一个真实任务能不能交付"，这次只回答"改完之后这条链还成立吗"。订阅消耗 **$0.14**。

## 一、拓扑与部署

| 角色 | 机器 / 账号 | 这一轮装的 |
| --- | --- | --- |
| Operator | 本机 xdwmbp / `bing` | `~/.local/bin/ccnm` |
| Agent Identity | fodelf / `fodelf` | `~/.local/bin/ccnm` + Controller |
| Runtime Executor | 本机 xdwmbp / `ccrun` | `~/.local/bin/ccnm`，以及 Agent 实际调用的 `/Users/Shared/ccnm-p7-20260910/bin/ccnm` |

**替换前的记录**（回退副本都在各自的 `~/.local/bin/ccnm.pre-batch-e`）：

```text
旧构建  sha256 1c14492ded87f59c340a8b3026ddba7d6a17c022793678ad9b68e114cc8178c7   三端一致
新构建  sha256 d9c8c8cc15936b55545d2d023b8fb6de87a4b5398e47e8f05825b5ef667c55e4   commit 9882938
两者的 `ccnm --version` 都是 0.2.0
```

版本字符串一样，所以**核对的是哈希，不是版本号**——这正是 P7.3 那次"controller 没换掉却看不出来"的教训。落地一律 `.new` + `mv`，不在原 inode 上写。

Controller 重启后 pid 53233 → 1330，`ps` 显示它起于二进制 mtime 之后、跑的是新路径，且全机只有这一个。

### 一件必须先做的事：删掉 `ccrun` 的出站私钥

P7.3 那条链要求 Runtime 侧拨号去 Agent，所以 `ccrun` 名下有一把 `~/.config/ccnm/transport/agent-key`。新链路不需要它，**删掉之后再验**才有意义：

```text
删除前  ~/.config/ccnm/transport/{agent-key, agent-key.pub}
删除后  ~/.ssh/{authorized_keys, config, known_hosts} + ~/.config/ccnm/config.toml —— 只剩入站状态和配置
        SSH_AUTH_SOCK: <unset>
```

## 二、验证结果

### 1. Operator public CLI → Agent → ccrun

以 **bing**（不是 ccrun）跑 `ccnm run p7parity --print`，让 Agent 在工作树里写一个带一次性 token 的文件：

```text
claude exited 0 in 9.2 s，3 turns，$0.10，0 permission denials
产物 e-cli.txt   owner=ccrun(uid 504)   内容 == cli-bbfe7951fdf7
```

### 2. `ccnm rpc` → Agent → ccrun

同一个 workspace，另一个 token，走 machine API（`clients/python/ccnm_machine_client.py`）：

```text
hello → agents.list → session.start(start_key) → wait → session.result
state completed，exit_code 0，usage {input 6, output 253}，cost $0.038492
产物 e-rpc.txt   owner=ccrun(uid 504)   内容 == rpc-8e57ff571dbd
```

**两条腿产物属主相同（都是 504）**，这是"两个公开入口落在同一条隔离执行链上"的判据。响应里 home 路径 / `.claude` / `.codex` / `auth.json` / 私钥名 / `session_dir` / `controller` 出现 **0 次**。

### 3. Agent Node 上的 `ccnm doctor`（D2 的正题）

在 fodelf 上跑，不再把公共命令送回 Runtime：

```text
Workspace config   OK   answered by runtime: agent=agent/claude-main, root=/Users/ccrun/p7-dogfood
Runtime user       OK   ccrun
No SSH keys        OK   no accessible private key candidate in ~/.ssh and ~/.config/ccnm; …
No Docker socket   OK   a Docker socket exists but this account cannot reach it, so it cannot write to it either
exec_command       OK   the runtime account is confined
Workspace root     OK   /Users/ccrun/p7-dogfood is a git repository ccrun can work in
Remote MCP handshake OK initialize in 1173 ms, 7 tools, pid 70778 throughout
→ 0 failed，2 not checked
```

**两个方向的结论逐字相同。** 同一个 workspace（`p7parity`）分别从 Runtime Node（Operator=bing）和 Agent Node 跑 doctor，取全部 Runtime 相关行做 `diff`：**空**。包括那一行 FAIL 也一模一样。

### 4. remote `ccnm mcp probe`（同样从 Agent 发起）

### 5. 执行身份没有出站，链路是 protocol 4

会话活着的时候连拍三张 `ccrun` 的进程表（间隔 5 秒）：

```text
75918  sshd-session: ccrun@notty                      ← 入站，Agent 连进来的
75939  …/bin/ccnm internal mcp-serve --payload …      ← 它的子进程
```

**没有任何 ssh 客户端进程。** payload 解出来是：


**没有 `root` 字段**——Batch B/C 那条"调用方不许说项目在哪"在真机上成立。

## 三、真机才看得见的三件事

### 1. Operator 是普通管理员账号，doctor 依然全绿

跑 doctor 的 `bing` 是 admin、有一堆 SSH 私钥、能读 Claude 凭据——**同一条命令在 P7.4 之前会报 7 个 FAIL**，因为那些行判的是敲命令的人。现在它报的是 `ccrun`：`Runtime user OK ccrun`、`No sudo OK`、`Not an admin OK`。这是 Batch D 在真机上的确认。

### 2. 新的 `Workspace root` 抓到了 P7.3 那个洞

`p7parity` 的工作树是 bing 拥有的 git 仓库，目录 0777 所以 ccrun 写得进去。旧检查只看"是不是目录"，绿。新检查：

```text
Workspace root  FAIL  CCNM_E_WRONG_WORKSPACE: /Users/Shared/ccnm-p7-20260910/parity is a
                      directory for ccrun, but git refuses it: the repository belongs to
                      another account
                      fix: make the project directory owned by ccrun, the identity that runs its tools
```

这正是 dogfood 那轮撞了半天的 `detected dubious ownership`，现在一行就说清了。**这个 FAIL 是留着的**：它是证据，不是待修的环境问题。

### 3. `ccrun` 没有私钥，但仍然连得到 Agent Node —— 这条必须说清楚

删掉私钥之后，从 `ccrun` 试着 ssh 到 fodelf，**成功了**：

```text
debug1: identity file /Users/ccrun/.config/ccnm/transport/agent-key type -1
debug1: no identity pubkey loaded from …/agent-key
debug1: Remote protocol version 2.0, remote software version Tailscale
Authenticated to fodelf.taila864e6.ts.net using "none".
landed as fodelf
```

答话的是 **Tailscale SSH**，它按 tailnet 身份授权，不看密钥。所以这台机器上任何本地账号都能到 fodelf，跟 ccnm 给不给它钥匙无关。

准确的说法只能是这两句，不能合并成第三句：

- **ccnm 不再要求 `ccrun` 出站**，它名下也没有 ccnm 所需的私钥或 SSH agent —— 这一条已验证；
- **`ccrun` 在这台机器上仍有出站能力**，来自主机的 Tailscale SSH 策略 —— 这是网络策略层的事，ccnm 管不了，[生产安全](../production-safety.md)里"网络出口是单独一层"说的就是它。

要真的关掉，得在 tailnet ACL 或 OS 网络策略上做，不属于本轮授权范围。

## 四、这一轮没有验的

- **Codex 经 machine API**：仍然从未发生过，等 xdwmbp 额度（P7.3 的缺口）。
- **Agent 侧发起的 `ccnm run`**：Batch C 改的另一半。它的 resolve 那一步被 doctor / mcp probe 共用并已验证，但"从 Agent 起一个真实会话"这一轮没跑（不在授权清单里，也会多花额度）。
- interactive 模式、Ctrl-D、egress 策略、完整项目 dogfood：都没做。
- 只在 macOS 上，只有这一套两端拓扑。
